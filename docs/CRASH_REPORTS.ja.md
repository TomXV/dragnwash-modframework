# クラッシュレポート

[English](CRASH_REPORTS.md)

> **実験的。** `experimental/d3d12-trace` ブランチにあり、まだリリースには入っていません。

ゲームが落ちると、その直前に何が起きていたかはたいてい失われます。BepInEx のログは途中で止まり、Unity のクラッシュフォルダーにはネイティブのスタックがあっても、どの Mod が何をしていたかは分かりません。中核は各セッションの短い記録を残し、ゲームがきれいに終了しなかったときにそれをレポートにします。すべてこの PC の中だけに置きます。

## 記録するもの

`BepInEx/CrashReports/session.log` に 1 行ずつ書き、書くたびにすぐディスクへ流すので、落ちても最後の行が残ります。

```
04:22:07.528 f18344 main scene loaded 'Wash' (Single)
04:22:07.611 f18351 main unity-error NullReferenceException: ...
04:22:09.002 f18470 main beat 16.7 ms/frame
```

- 開始時：フレームワークと Unity のバージョン、グラフィックス API とグラフィックスカード、画面モード、起動オプション。続けて、読み込まれたすべての Mod とそのバージョン。
- シーンの読み込みと破棄、Mod のリロード。
- Unity のエラー、例外、グラフィックスデバイスのメッセージ。
- 10 秒ごとの生存確認（GPU 転送のトレース中は 1 秒ごと）。最後の記録からどのくらいあとにゲームが止まったかが分かります。
- Mod が `CrashReports.Note(ownerGuid, category, message)` で残す記録。

きれいに終了すると、ファイルの最後に `END clean exit` と書きます。長いセッションでは 4 MB で次のファイルに切り替え、前の分を `session.1.log` として残します。

## レポート

次の起動時に、`session.log` の最後にその印がなければ、ゲームは落ちたか、固まって手で閉じられたか、強制終了されたということです。中核は `BepInEx/CrashReports/<日付>_<時刻>/` に次のものを書きます。

- `report.txt`：いつ終わったか、バージョンと Mod、最後の 40 件の記録、そして Unity 自身のクラッシュフォルダー（`%TEMP%/<会社名>/<製品名>/Crashes/Crash_*`）が終了から 2 分以内に作られていれば、そのネイティブのスタック。
- `session.log`（切り替えがあれば `session.1.log` も）。
- `crash.dmp`：Unity 自身のクラッシュのメモリダンプ。クラッシュフォルダーからコピーします。

レポートの場所はログに出ます。レポートは最新の 10 件を残します。不具合を報告するときは `report.txt` を添えてください。

## クラッシュレポートのウィンドウ

Windows では、中核が `CrashReporter.exe`（中核の DLL の隣）も起動します。ゲームの外にある小さなプログラムで、ゲームが閉じるのを待ちます。きれいに終了したときは、何も残さずに消えます。そうでなければ Unity のクラッシュハンドラーが書き終えるのを待ってレポートを書き（中核が次の起動時に走らせるのと同じコードです。先に書いたほうが記録に「報告済み」と印を付けます）、すぐに専用のウィンドウで見せます。言葉は Windows の表示言語に合わせて、英語・日本語・中国語です。

- **何が起きたか**を言葉で：Direct3D 12 の既知のクラッシュ（UUM-140564）、グラフィックスデバイスの応答停止、フリーズ、クラッシュなしの停止（強制終了、電源断）、その他の Unity 内のクラッシュ。
- それに対して**できること**（あれば）。
- 詳しい情報（日時、シーン、プレイ時間、最後のエラー、グラフィックス）と、レポートの場所。
- **レポートのフォルダーを開く**、**レポートをコピー**（report.txt。不具合の報告用）、**閉じる**。

ウィンドウはゲームではなく Windows が描くので、ゲームがどう止まっても出せます。Wine や Proton（Steam Deck、Linux）では起動しません。そこでは次の起動時にレポートを書きます。`CrashReporter.exe --show <レポートのフォルダー>` でレポートをもう一度開けます。`[Diagnostics] CrashReporterWindow` でオフにできます。

## メモリダンプ

ダンプは、ゲームのプロセスのスナップショットです。すべてのスレッドのスタックと、読み込まれていたモジュールが入っていて、デバッガー（WinDbg、Visual Studio）でゲームの PDB ファイルと一緒に開けます（ゲームには `UnityPlayer_Win64_player_mono_x64.pdb` が同梱されています）。ログでは分からない「おかしくなったとき、各スレッドがどこにいたか」が分かります。

- **クラッシュ**：Unity 自身が `crash.dmp` を書きます。レポートにはそのコピーを入れます。
- **フリーズ**：ゲームが固まったとき、Unity は何も書きません。そこで見張り役のスレッドが書きます。ゲームの窓が前面にある状態で、メインスレッドが 15 秒間 1 フレームも進まなかったら、プロセスのミニダンプ（数 MB、Windows）を `BepInEx/CrashReports/<日付>_<時刻>_hang/` に書き、セッションの記録にもそう書きます。ゲームがまた動き出したら、それも記録します。裏に回っているゲームは数えません。わざとフレームを止めていることがあるからです。

ダンプにはゲームのメモリの一部が入っています。**調べる人にだけ個別に渡し、公開の Issue には添付しないでください。** 公開の報告に添えるのは `report.txt` です。

## 設定

オプション → Mods → Drag'n Wash ModFramework → **Diagnostics**（Crash reports と Trace GPU uploads は次の起動から効きます）：

- **Crash reports**（`[Diagnostics] CrashReports`、オン）：記録とレポート。
- **Crash report window**（`[Diagnostics] CrashReporterWindow`、オン）：Windows での専用ウィンドウ。
- **Memory dump when the game freezes**（`[Diagnostics] HangDumps`、オン、詳細設定）：見張り役のダンプ。
- **Trace GPU uploads**（`[Diagnostics] TraceGpuUploads`、オフ、詳細設定、実験的）：テクスチャの転送と作成、動的フォントと TextMeshPro のアトラスの拡張、メッシュの転送、アセットバンドルの読み込み、解放された GPU のリソースのすべてについて、大きさと、呼び出し元の Mod を記録に足します。Unity のメソッドにパッチを当て、そのたびにスタックをたどるので、調べるときだけオンにしてください。

## なぜ：Direct3D 12 のクラッシュ

Direct3D 12 では、この Unity のバージョンはレンダリングのスレッドで `D3D12ScratchAllocator::DestroyScratch` で落ちます。GPU への転送が通る一時的なメモリ（scratch）を、あるフレームが `ReleaseExcessScratch` で切り詰めるときです（Unity の不具合 UUM-140564）。メンテナの PC にあるクラッシュフォルダー（2026-09-11〜09-16 の 30 件）はすべてこのスタックで、その直前はオプションか Tool window を開いたところでした。どの転送が一時メモリを増やすのかはまだ分かっていません。*Trace GPU uploads* はそれを突き止めるためのものです。分かれば、遊ぶ人に `-force-d3d11` を勧めるだけでなく、フレームワークの側でその転送を避けられます（分ける、起動時に移す）。

## Mod 作者向け

```csharp
CrashReports.Note(MyPlugin.Guid, "load", $"importing {count} textures from {folder}");
```

記録は軽く、どのスレッドからでも安全に呼べます。重い処理や危ない処理の前に 1 つ残しておくと、その直後に落ちたときに手がかりになります。短く書き、個人情報は入れないでください。レポートは公開の不具合報告に添えるためのものです。
