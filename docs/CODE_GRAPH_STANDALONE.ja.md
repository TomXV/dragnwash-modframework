# ゲームなしで使うコードのグラフ

[English](CODE_GRAPH_STANDALONE.md)

> **調査と試作をしました**（実験的、2026-09-20）。ブランチ `experimental/code-graph-standalone` にあります。試作は Windows で動きます。リリースには入れていません。最終的にどこに置くかは[未決](#未決のこと)です。

[コードのグラフ](CODE_GRAPH.ja.md)は、メソッドをブロックと分岐として、呼ぶもの、呼ばれるところ、フィールドとともに描きます。今はこれが Drag'n Wash の中でしか動きません。Inspector がグラフを作り、Bridge がページを出しているからです。ただ、描くこと自体にはゲームは要りません。ですから同じグラフで、**どの .NET アセンブリも**見られます。ほかの Unity ゲームの `Managed` フォルダー、Mod、ライブラリー、自分の DLL などです。この記録には、そのために何を切り分けるか、ゲームなしでページがどうデータを受け取るか、試作が何をするかを書きます。

## 決めたこと

2026-09-20 にオーナーが決めました。

1. **置き場所：実験的なあいだは、このリポジトリの `codegraph-standalone/`。** 共有するファイルは 1 か所から両方のビルドに入るので、グラフの修正は 1 つのコミットで Inspector とアプリの両方に届きます。ゲームを遊んだことのない人から issue が来る、独自にリリースする、というように自分の利用者を持つようになったら、モデルとページを持って専用のリポジトリへ移します。そうすれば、どちらももう一方を背負いません。フレームワークはゲームだけが知ること（パッチ、リスナー、ゲームのアセンブリ）を、ツールは残りを持ちます。
2. **名前は Code Graph。** 窓にも、ページの見出しにも、Windows が出す情報にも、ゲームの名前は入れません。ファイル名はこのリポジトリでは `CodeGraphStandalone.exe` のままにします（Bridge の隣にあるゲーム用の `CodeGraph.exe` と取り違えないため）。単独で配る zip の中では `CodeGraph.exe` という名前でかまいません。
3. **Unity の外での Unity メッセージ：** モデルは今のままにします（Inspector の答えが変わってはいけないので）。Unity のゲームでない DLL の `Update` や `Awake` には誤った印が付きますが、基底の型をたどって「MonoBehaviour か」を問うフックは、Unity 以外のコードで本当に使うようになってから足します。
4. **単独で配ります。** ツール自身の zip として出し、ゲームを遊ぶ人のためのフレームワークの zip には入れません。

## 共有するもの、切り分けるもの

| 部分 | 場所 | 必要なもの |
|---|---|---|
| **`CodeGraphModel`**：索引（メソッド、型、呼び出し元、ステートマシン）、`code.graph`、`code.type`、`code.callers`、`code.search` をページの JSON で | `src/DragNWash.ModFramework.Inspector/CodeGraphModel.cs`。Inspector でビルドし、アプリにはリンクで入れます | Mono.Cecil と .NET だけ |
| ゲームの側：どのアセンブリがゲームのものか（`Application.dataPath`、除外の一覧）、Harmony のパッチとその Mod、読み込まれたシーンの UnityEvent のリスナー、ログ、操作の登録 | `InspectorCodeGraph.cs` | Unity、Harmony、BepInEx、フレームワーク |
| ページ | `src/DragNWash.ModFramework.Bridge/Page/page.html`。Bridge とアプリの両方に埋め込みます | ブラウザーのエンジン |
| アプリ：ファイルを開き、ページに答える | `codegraph-standalone/` | WebView2、Mono.Cecil（NuGet） |

ゲームだけが知ることは、3 つの設定でモデルに渡します。`Patches`（メソッドの id からそのパッチを引く表。グラフごとに 1 回作ります）、`Listeners`（ほかにそのメソッドへ来るもの）、`Source`（「No type … in the game's assemblies」の言葉）です。空のままなら、グラフにパッチもリスナーも出ません。ほかは何も変えていません。Cecil 用とリフレクション用の `Id()` は（一致していなければならないので）一緒に移し、`InspectorCodeGraph.Id()` はそれを呼ぶだけにしたので、Code 表示はそのままです。

**Inspector の答えは前とまったく同じです。** ゲームの外で確かめました。`main` のコード（Harmony とシーンの部分を空のものに替えたもの）と新しいモデルを並べて、ゲームの 15 のアセンブリで、すべてのメソッド（本体とスタブの両方）、その呼び出し元、すべての型、いくつかの検索、いくつかの誤った名前を試しました。18,751 の答えが、エラーも含めて JSON としてすべて一致しました。わざと変えたメッセージは検出されました。パッチとリスナーのコードは移しただけで変えていません。これを試すにはゲームが要ります（下記）。

## ファイルとフォルダーを開く

- **ファイル**：DLL か EXE を 1 つ、または複数（Open… → Assemblies…、コマンドライン、窓へのドロップ）。
- **フォルダー**：中の `.dll` と `.exe` です。.NET と Unity 自身のもの（`System*`、`Microsoft.*`、`mscorlib`、`netstandard`、`Unity*`、`Mono.*` など）は、ほかに何もない場合を除いて外します。`--all` で残します。外したものへの呼び出しは一覧には出ますが、開けません。
- **Unity ゲームのフォルダー**（またはその `_Data` フォルダー）：その `<名前>_Data/Managed` フォルダーを、上と同じように開きます。
- **IL2CPP のゲーム**（`GameAssembly.dll` があり、`Managed` がない）：理由を示して断ります。コードがネイティブなので、描く IL がありません。この PC にある Unity のゲーム 6 本のうち 3 本が IL2CPP でした。
- フォルダーの中の**ネイティブの DLL** は飛ばし、数を示します（.NET のランタイムのフォルダーには 13 あります）。
- ファイルはメモリーに読み込む（`InMemory`）ので、ロックされず、開いたまま作り直せます。**Read again** は同じパスを読み直し、表示中のメソッドに留まります。

コマンドライン：`CodeGraphStandalone.exe [file.dll …|folder] [--focus m:<method>|t:<type>] [--all]`。

## ゲームなしでページがデータを受け取る方法

ページは `POST /page/api/op` に `{ name, args }` を送り、`{ ok, value | error }` を読みます。答え方を 4 つ、試すか調べました。

| 方法 | 結果 |
|---|---|
| 窓の中にしかないアドレス（`https://codegraph.example/…`）への **WebView2 の `WebResourceRequested`** | **採用。** ページとその呼び出しに、アプリのプロセスの中で答えます。ページはそのまま（同じオリジンへの `fetch`）で、POST の本文も届き、ポートは開きません（確かめました：アプリは何も待ち受けていません）。1 回の呼び出しの往復は、50 回のグラフで中央値 0.8 ms、最大 14 ms でした。 |
| `SetVirtualHostNameToFolderMapping` | フォルダーのファイルを出すだけで、ページの POST には答えられません。結局ほかの方法も要ります。ページは exe に埋め込んでいるので、そもそも要りません。 |
| 両方向の `chrome.webview.postMessage` | 動くはずです（試していません）が、ページの `call()` に、`fetch` と歩調を合わせたもう 1 つの通り道（id、返事）が要ります。上の方法より良い点がありません。 |
| この PC のための HTTP サーバー | 普通のブラウザーにはこれしかないので、Linux と macOS ではこれです（下記）。ほかのページやプログラムからも呼べてしまうので、Bridge の入口（一度きりの合言葉、Cookie、Origin と Host の確認）がもう一度要ります。 |

ページは、アプリがページのスクリプトより先に設定する `window.dnwHost` で、自分がアプリの中にいると知ります。見出し、状態の行、案内の言葉がアプリのものになり、アプリのメニューを出す **Open…** ボタンが出ます。`dnwHost` がなければ（ゲームの中でも、ブラウザーでも）、ページは一字一句前と同じです（ブラウザーで確かめました）。

ファイルのドロップ：ドロップはページに届き、ページはドロップされたファイルを `chrome.webview.postMessageWithAdditionalObjects` でアプリに渡します。WebView2 がアプリに本当のパスを教えます。このスクリプトはアプリが足すもので、ページには書いていません。

## Linux と macOS（設計だけ）

モデルは .NET 8 と Mono.Cecil 0.11.4 でもビルドでき、同じグラフを出します（ゲームのアセンブリで確かめました：ブロックは同じ、時間もほぼ同じ）。違うのは窓です。

- **おすすめ：システムのブラウザーでページを開き、小さなコンソールのホストが出す**（`net8.0`。Windows でも動きます）。`codegraph-standalone serve <paths>` が `127.0.0.1` の空いているポートで待ち受け、ブラウザーで `/page#code=<一度きりの合言葉>` を開き、Bridge のページと同じサインインを使います（合言葉 → `HttpOnly`、`SameSite=Strict` の Cookie。以後の呼び出しには Cookie と正しい `Origin`、正しい `Host` が要ります）。ファイルはコマンドラインで開きます（ブラウザーはパスを渡せません）。そのときは入口の処理も、モデルと同じやり方で Bridge と共有し、二度書かないようにします。
- ネイティブの窓（WebKitGTK、Photino）：システムごとに依存が 1 つ増えるわりに、ブラウザーより良い点がほとんどありません。
- Steam Deck では、デスクトップモードでブラウザーの方法が使えます。

## ゲームの外で失うもの、得るもの

**失うもの：** Harmony のパッチ（Mod が読み込まれていないため）、UnityEvent のリスナー（シーンがないため）、そのほか動いているゲームだけが知ること。グラフには「Patches on it (0)」と出て、「Events that lead here」には Unity メッセージだけが出ます。

**得るもの：** Mono でビルドされたどの .NET アセンブリも（ほかのゲーム、Mod、BepInEx 自身、自分のコードも）。ゲームを動かさなくてよく、Bridge もトークンも要りません。オフラインで動きます。逆コンパイラーは使いません（ゲームの中と同じく、ソースではなく構造です）。

## 安全

- 読むのは利用者が開いたもの（ダイアログ、ドロップ、コマンドライン）だけです。書くのは、窓の WebView2 のプロファイル（`%LOCALAPPDATA%\DragNWash ModFramework\CodeGraphStandalone`）だけです。
- ポートもネットワークも使いません。ページのアドレスにはプロセスの中で答えるので、ほかのプログラムや Web ページは届きません。ほかのアドレスへの移動も新しい窓も断り、DevTools とホストオブジェクトは切ってあり、ページには Bridge と同じ Content-Security-Policy を付けます（インターネットからは何も読みません）。
- ページが指定できるのは操作とその引数だけで、ファイルを求めることはできません。
- AI クライアント向けではありません。ゲームのグラフと同じく、MCP には出しません。

## ライセンスとコンテンツの方針

- アプリはほかと同じく MIT です。CodeGraph.exe と同じく、Mono.Cecil（MIT）と Microsoft の WebView2 SDK を同梱します。
- **他人のコードは決して配りません。** リポジトリ、リリース、ドキュメント、スクリーンショット、テストには、自分たちのものでないアセンブリから読んだものを一切入れません。グラフも IL も名前もです。テストにはアプリ自身のアセンブリか、テストのために作ったアセンブリを使います。下の測定は数と時間だけを載せています。
- 見せるのはソースではなく構造で、書き出す機能はありません。ほかのプログラムのコードで利用者が何をしてよいかは、このツールではなく、そのプログラムのライセンスが決めます。アプリは何もどこにも送らないと表示し、実際に送りません。
- Drag'n Wash 自身については[コンテンツの方針](CONTENT_POLICY.ja.md)は変わりません。ゲームのコードは利用者の PC の中に留まります。

- メモリーはメソッド 1 つにつき約 3 KB で、索引は一度に全部作ります。フォルダーを開くとき .NET と Unity 自身のアセンブリを既定で外すのはこのためです。`Managed` 全体の 3.2 秒のうち 1.2 秒は、Cecil が本体を解読する時間です。

- Mono.Cecil 0.10.4（BepInEx のもの）と 0.11.4（NuGet）のどちらでも上のすべてを読めました。共有するファイルは両方でビルドできます。

## 試作

`codegraph-standalone/`（net472、x64、WinForms と WebView2。CodeGraph.exe と同じく決定的にビルドします）：

- `Program.cs`：コマンドライン。
- `Opened.cs`：ファイル、フォルダー、Unity ゲームのフォルダー、IL2CPP とネイティブの DLL を扱い、1 つの `CodeGraphModel` にします。
- `ViewerForm.cs`：窓、`WebResourceRequested` によるページとその呼び出し、Open…（アセンブリ、フォルダー、読み直し）、ドロップされたファイル。
- `codegraph/WindowChrome.cs`：両方のアプリでビルドします。2 つの窓が共有する、暗いタイトルバーと WebView2 の設定。

Windows で、WebView2 の DevTools プロトコル（テストのときだけ開けたデバッグ用のポート）で窓を動かして試しました。ゲームのアセンブリの型とメソッドの表示、検索、ステートマシンを通したコルーチン、知らない操作のエラー、ほかのパスへの要求（404）、DLL、フォルダー、Unity ゲームのフォルダー、IL2CPP のゲームのフォルダーのドロップです。
